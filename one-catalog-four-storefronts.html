One catalog, four storefronts: how the generator keeps it honest

The same packs list on four storefronts: Fourthwall, Getly, SellApp and Gumroad. The product catalog page that ties them together was hand-edited until this week, and hand-edited pages drift. An audit caught the drift in three places: seven listings missing a sentence, a product count stuck six behind the truth, and a $7 line counted twice. The page is generated from one data file now.

Three ways a catalog lies

Stale text. A five-pack bundle gained one sentence on its Fourthwall listing: the same packs sell together as a bundle at $29 instead of $45, see the bundle listing in this store. The sentence went in after the other storefronts' descriptions were written, so seven listings never saw it, three on SellApp and four Gumroad drafts. Seven description-only patches fixed them, each read back from the API to confirm it landed. One Getly description still lacks the sentence, 967 characters against the Fourthwall listing's 1,113, and it waits on the cache rule below.

Stale counts. The hand-edited page said 84 SKUs while the portfolio behind it kept growing, and llms.txt carried the same stale 84 in two places. When the generator first ran the real count was 87; three more products flipped live that same day and it moved again, to 90.

Double counting. The status header carried a $7 wallpaper pack twice, once inside a wallpaper series and once as a named line item. The ledger's row-by-row math closed without the extra $7.

Nobody typed these on purpose. They happen when one fact lives in five files and every product push edits one of them.

One file, one page

The fix puts every public product in one place, portfolio.json: 100 rows, each with a status and the store URLs. gen-products.py reads it and renders the whole catalog page. The include rule is four lines:

live = [r for r in rows
        if r['status'] == 'LIVE-FOURTHWALL'
        or (r['status'] == 'LIVE-GETLY' and (not pending(r) or r.get('fourthwall_url')))]

A Getly upload stuck in platform review still ships if its Fourthwall offer is live, linked through Fourthwall. A pending upload with no live channel, Gumroad drafts, queued and discarded rows stay off the page, and the hero lead states how many are waiting. Every count on the page is computed from those rows: meta description, og tags, JSON-LD, lead, stats strip. The number that sat at 84 for weeks cannot appear anywhere now unless the portfolio says so.

Fail loud, then prove nothing moved

The generator refuses to guess. A live product missing from the group table aborts and prints the folder names. A missing copy entry aborts. A duplicate entry aborts. Copy for an off-page product prints a warning. The failure mode is a red run and zero deploy instead of a page that silently drops a product:

ERROR: live product(s) missing from GROUPS: budget-tracker, halloween-bundle

That abort fired in real life. Three products flipped live between renders, and the page stayed at 87 until their copy entries were written, the lag visible in the data the whole time. Two runs in a row produce byte-identical output. The freeze test rendered the portfolio without the three newest rows and diffed it against the deployed page. One line differed, the lead sentence whose pending count had really changed that day. All 84 older cards were byte-identical.

The cache rule that keeps Getly edits away

Getly storefront pages are Next.js. While a listing sits in review, its public URL can serve a cached 407 with s-maxage=604800, seven days. Flipping the status does not trigger revalidation, and neither does patching the description. So the rule is to check status through the API and never GET a pending listing's public URL. The control case held, a wedding pack that was never probed while pending answered 200 in every locale the day it went active. The short Getly description stays untouched until that listing turns active.

What still needs a human

The generator renders the page; it refuses to write copy. Every new product needs a hand-written entry: a niche chip like "CSV · 8 cities", a description with the item count verbatim from the listing, an optional alternate-store link. The page cannot show a number the portfolio does not support, and it cannot grow until someone writes the new product's copy.

llms.txt is the remaining hand-edited neighbor, and it drifted again while this article was in publish. The page said 90, the text file still said 87 from the previous render. Two lines, resynced in the same commit as this article's deploy. The next fix gives that file the same treatment as the page, read the portfolio, render the counts.

The files get checked too

Text drift is one way a catalog lies to a buyer. Broken files are another. Thirteen product PDFs once shipped because QA counted stream objects while the page tree pointed at fonts, so files full of streams still rendered blank. The fix walks the page tree, every /Kids entry resolving to /Type /Page, every /Contents to a stream, no orphans, /Count matching, and it runs on every PDF pack before publish. That walk ships free as pdfcheck-mcp, the same fixture method guarding this catalog's printables.

What I'd hand myself a month ago

  • One fact, one file. A count that lives in two places is two chances to be wrong.
  • Byte-compare beats eyeballing. Render, diff, ship.
  • Abort on missing data beats rendering with gaps; a red run lists the folders to fix.
  • Pending platform pages: API for status, eyes off the public URL.
