README Template for GitHub

A README has one job: get a stranger from "found the repo" to "running the thing" without asking you a question. Below is the 7-section structure we think holds up for most projects, why each section earns its spot (labeled as opinion where it is one), and a copy-paste markdown skeleton at the bottom. Replace the brackets, delete what does not apply, ship.

How to use this page: skim the table to see which sections fit your project, then copy the template block into your README.md and work top to bottom. Every [BRACKET] is a blank you fill with your own facts. Nothing in brackets is a claim, so an unfilled bracket can only fail loudly, never quietly lie.

The 7 sections, and why each one is there

SectionWhy it earns its spot
OverviewTwo or three sentences on what the project does and what it outputs. This is the only paragraph every visitor reads, so it carries the decision to keep scrolling. Opinion: if it takes five sentences, the project probably needs a docs site, not a longer README.
QuickstartThe shortest path from clone to a working command, written as copy-paste blocks. Most README failures happen here: no install steps, or install steps that assume things only the author has. Opinion: a working quickstart is worth more than any feature list.
ArchitectureWhere the main parts live and how they connect: entry points, data flow, one diagram or one paragraph. It answers "where do I even look" before someone greps the tree. Optional for single-file scripts, near-mandatory once a second contributor shows up.
SecurityWhat the project touches (keys, funds, personal data, network), what is audited and what is not, and how to report a problem. Writing "unaudited, do your own review" plainly beats silence, because silence reads as a promise you never made.
TestingHow to run the tests and what coverage exists. This is how a reviewer checks whether the project can be changed safely, and it is the first thing people open after the quickstart breaks for them.
ContributingBranch conventions, how to open an issue, what a good pull request includes. Short is fine. Without it, every contribution starts with a question in your inbox instead.
LicenseOne line naming the license and pointing at the LICENSE file. Without it, the default is "all rights reserved", and nobody can legally reuse anything, which is usually the opposite of why the repo is public.

The order matters less than the presence of each section. We put quickstart near the top because visitors who bounce usually bounce before finding a runnable command. That placement is an opinion, not a rule; a docs-first project can invert it.

Copy-paste template

Plain markdown, works on GitHub, GitLab, or any docs site. Placeholders are [BRACKETS]; install commands are left generic on purpose, since the right steps depend on your stack.

# [YOUR-PROJECT-NAME]

> [One line: what this project does and what it outputs.]

[Badges: keep 3-5, only ones that stay true - license, build status, version.
Link them to your own status pages, not to numbers you have to update daily.]

## Overview

[YOUR-PROJECT-NAME] is a [type: tool / library / app / dataset] for
[task it solves]. Output: [what the user gets]. This repo contains
[what is actually in here].

## Quickstart

```bash
# clone
git clone https://github.com/[YOUR-ORG]/[YOUR-REPO].git
cd [YOUR-REPO]

# install - write the real steps for your stack
[install step 1]
[install step 2]

# run - the first command most users need
[run command] --help
```

Requires: [language/runtime version, OS notes if any].

## Architecture

[One paragraph or one diagram: main components, how they connect,
where the entry point lives.]

- `[src/]` - [what lives here]
- `[docs/]` - [what lives here]

## Security

What this project touches: [keys / funds / personal data / network].

- Audit status: [audited by whom, or "unaudited - review before production use"]
- Reporting: [how to report a security issue, e.g. open a private advisory or email [CONTACT]]

## Testing

```bash
[test command]
```

Covers: [what the tests actually check, and what they do not].

## Contributing

[Branch conventions, how to open issues, what a pull request needs.
Two lines is fine.]

## License

[MIT / Apache-2.0 / GPL-3.0 - see LICENSE.]

Three mistakes we see most in project READMEs (honest list, from reviewing a lot of them):

  • No install steps at all. The visitor finds a description, a license, and no way to run anything. If your quickstart says "see the docs", the docs link needs to be one click from working, or the quickstart does not exist.
  • Walls of text before the first command. Long motivation paragraphs push the runnable part below the fold. Most visitors decide in seconds whether the repo is for them; let the quickstart make that case.
  • Stale badges. A build badge that has been failing for a month or a version badge frozen two releases back reads as an abandoned repo. Keep badges few and check them when you tag a release, or drop the ones you will not maintain.

This list is our own observation from reading repo READMEs, not survey data. Your project may honestly need none of the fixes above; the checklist is a starting point, not a score.

Four tips for a README that holds up

1. Put a screenshot above the fold. Our take: one image of the thing working (terminal output, UI, chart) answers "is this real" faster than any paragraph. GIFs work too, but keep them under a couple of megabytes or the page loads like a slideshow.

2. Write the quickstart before the overview. Opinion, not a rule: draft the install-and-run steps first, then write the intro to match what the steps do. Drafting in the other order tends to produce an overview that promises a quickstart the repo does not have.

3. Fill the security section even for toy projects. Two honest lines ("unaudited, keys are read-only, file issues privately") cost nothing and prevent the worst kind of assumption. Silence is where people read in what they hope is true.

4. Re-read your own README like a stranger, after shipping. Our take: the author's version of the README is always missing the step the author does without thinking. Follow your own quickstart on a clean machine or a fresh container once; every step you skip by reflex is a step a stranger cannot do.
