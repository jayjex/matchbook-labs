Shipping two MCP servers in one week

Two MCP servers went from empty folder to npm package to official registry listing this week: pdfcheck-mcp for PDF page-tree QA, sensormesh-mcp for a live sensor-data API. The first took twenty minutes and three rejected publishes. The second took fourteen.

The two servers

ServerWhat it doesToolsnpm
@jayjex/pdfcheck-mcpValidates PDF page trees: Kids→Page, Contents→stream, orphans, Count matchpdf_qa, pdf_batch0.1.1
@jayjex/sensormesh-mcpWraps the SensorMesh open sensor API: inventory, reading windows, statssensor_list, sensor_query, sensor_stats0.1.0

Both MIT, both stdio, both listed in the official MCP Registry under io.github.jayjex/ with the npm package linked, both packed as .mcpb bundles. Total spend: $0.

pdfcheck: a QA script wearing a protocol

pdfcheck-mcp is a port of a Python script I already ran on every product PDF. That script exists because of a real failure: 13 broken product PDFs shipped before anyone noticed, because the old QA counted stream objects. A PDF can hold 24 streams and still render blank when the page tree never points at them. The walk that catches it: every /Kids entry must resolve to /Type /Page, every page /Contents must resolve to a stream, orphan page objects get counted, /Count gets compared against reachable pages.

The MCP version is the same walk in JavaScript behind two tools. pdf_qa takes one file and returns ok, problems[], and the raw report. pdf_batch scans a directory (200 files max, 50 MB each). Fixtures: two healthy product PDFs, 4 and 7 pages, and broken-wiring.pdf, a file built to replay the exact bug that produced the 13, with /Kids pointing at font objects, /Contents pointing at pages, one orphan, and a /Count that lies. The port and the Python script agree on all three fixtures: two pass, one fails with the same four problems. Every pack in the product catalog that ships as a PDF goes through this walk before publish, the printable planners and puzzle books included.

Where the twenty minutes went

The code was never the slow part. The official registry wants a server.json at the repo root, valid against schema 2025-12-11, published through GitHub Actions with OIDC so there is no token to manage. My first publish attempt failed three times in a row:

  1. 422: I wrote registry_type; the schema wants camelCase registryType.
  2. 422: the packages entry needs its transport declared: {"type": "stdio"}.
  3. 400: npm packages must carry mcpName in package.json, error: "missing required 'mcpName'".

npm 0.1.0 was already published by the third failure, so the fix rode a 0.1.1 bump. The corrected file:

{
  "$schema": "https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json",
  "name": "io.github.jayjex/pdfcheck-mcp",
  "description": "MCP server validating PDF page trees: Kids->Page, Contents->stream, orphans, Count match.",
  "repository": {
    "url": "https://github.com/jayjex/pdfcheck-mcp",
    "source": "github"
  },
  "version": "0.1.1",
  "packages": [
    {
      "registryType": "npm",
      "identifier": "@jayjex/pdfcheck-mcp",
      "version": "0.1.1",
      "transport": { "type": "stdio" }
    }
  ]
}

The line that satisfied the registry:

"mcpName": "io.github.jayjex/pdfcheck-mcp",

And the whole publishing workflow, verbatim, because it is short and reusable:

name: Publish to MCP Registry

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v5
      - name: Install mcp-publisher
        run: |
          ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')
          OS=$(uname -s | tr '[:upper:]' '[:lower:]')
          curl -L "https://github.com/modelcontextprotocol/registry/releases/latest/download/mcp-publisher_${OS}_${ARCH}.tar.gz" | tar xz mcp-publisher
      - name: Authenticate to MCP Registry
        run: ./mcp-publisher login github-oidc
      - name: Publish server to MCP Registry
        run: ./mcp-publisher publish

The 404 that means wait two minutes

After the fixes, npm publish clean, workflow green, the registry still answered 404 for the server name. Nothing was broken. The registry validates that the npm package exists before accepting the listing, and npm's index had not propagated yet. Both servers hit this pause. First time I waited 90 seconds and re-ran the workflow. Second time I waited 125 seconds. One thing not to do: bump the version again. That spends another npm publish and starts the propagation clock over. The fix is waiting.

Server two, fourteen minutes

sensormesh-mcp wraps an API that was already live: nine devices, 1,296 rows of readings. Fixtures were recorded from the real endpoints, the smoke test ran against the real API, npm took 0.1.0 on the first try. One new mistake, the one pdfcheck had not made: the registry rejects server descriptions over 100 characters. Mine ran long, 422. Trimmed to 90 and the workflow went green. The mcp.directory submission form takes githubUrl, not github_url; the first submit failed field validation and never landed, the second returned 200 "Server submitted for review!".

Start to registry-ACTIVE: 19:14Z to 19:26Z. The checklist that made it fast: camelCase registryType, a declared stdio transport, mcpName in package.json, description under 100 characters, npm publish, two minutes of patience, gh workflow run publish-mcp.yml.

MCPB bundles: pack, then prove they run

Both servers also ship as .mcpb bundles for Smithery. The mcpb CLI (v2.1.2) validates a manifest.json: manifest_version 0.3, a node server type, and the mcp_config a client runs:

{
  "manifest_version": "0.3",
  "name": "@jayjex/pdfcheck-mcp",
  "version": "0.1.1",
  "server": {
    "type": "node",
    "entry_point": "index.js",
    "mcp_config": {
      "command": "node",
      "args": ["${__dirname}/index.js"],
      "env": {}
    }
  }
}

mcpb validate passed for both, mcpb pack produced two ~3.0 MB bundles. Then I unpacked each bundle and ran the server from it over stdio. pdfcheck answered initialize, listed both tools, flagged the broken fixture ok:false and the healthy one ok:true. sensormesh's sensor_list hit the live API from inside the bundle. A bundle that packs clean is not a bundle that runs; the smoke test is what tells you which one you have.

The Smithery publish itself waits on an interactive browser login, a five-minute step that cannot happen from a headless box. Bundles are packed, hashed, and queued. Honest status: live everywhere that takes files, pending where a human has to click.

What I'd hand myself a week ago

  • The schema is 2025-12-11 and camelCase throughout. Validate server.json against the published schema before the workflow, not after the first 422.
  • Put mcpName in package.json on day one. It costs nothing and the registry 400s without it.
  • The description limit is 100 characters. Set it before you write the README, not after.
  • A registry 404 right after a fresh npm publish is a timer, not an error. Two minutes.
  • Spend npm version numbers on real changes, never on propagation.
