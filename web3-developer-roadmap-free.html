Web3 developer roadmap: six stages from basics to shipping

A free guide to learning web3 development in an order that builds. Six stages, each with the skills in it and the point where you can move on, then a portfolio checklist and a case for hackathons as practice. If you want to learn web3 development without paying for a program, this page is the free path.

The six learning stages

Each stage is one row: the skills to pick up, and the moment you're ready for the next one. Move on at the checkpoint, not when you feel ready, because the feeling never arrives.

StageWhat to learnYou're ready to move on when
1. BasicsJavaScript or Python, HTML and CSS, reading JSON, working in a terminal.You can write a script that calls a free API and prints a formatted result.
2. ToolingGit and GitHub, a package manager, Node.js, an editor with a debugger.You can clone a repo, install its dependencies, and run its tests without help.
3. ContractsSolidity or Rust for your chain, that chain's official docs, a testnet wallet and faucet.You can deploy a toy contract to a public testnet and call it from a script.
4. TestingUnit tests for contracts, forked-chain simulation, writing the failure cases first.Every change you deploy goes through a red-green test cycle by habit.
5. InfraRPC endpoints and rate limits, reading contract events, wallet connection, secret handling with environment variables.A small dapp you wrote reads live on-chain data without keys hardcoded anywhere.
6. ShipScoping a small project, contract verification, a deploy checklist, collecting user feedback.A live project exists that a stranger can try without you explaining it in a call.

The stages compound, so skipping one shows up as a wall in the next. Stage 3 without stage 2 means wrestling Git while learning Solidity; stage 6 without stage 4 means shipping untested contracts. The chain itself matters less than the order, and the same stages work for Ethereum, Solana, Base, or Bitcoin ecosystems, since only stage 3 changes per chain.

Hackathons as practice

Once stage 3 starts feeling real, hackathons are the cheapest practice loop available: a deadline, a theme, and other builders to compare notes with. Treat them as reps, not as auditions. Portfolio checklist

Five items, in the order recruiters and collaborators actually check them. Copy these into your own notes and tick as you go.

  • ☐ One deployed project on a public testnet, with a README that names the chain and what it does.
  • ☐ A repo whose tests run green from a fresh clone, verified by asking a friend to clone it.
  • ☐ A short writeup of one bug you fixed: what broke, how you found it, what the fix was.
  • ☐ A pinned-repo selection a stranger can skim in two minutes and understand.
  • ☐ Your contact route stated on your profile, in one line, without a form nobody answers.

Four opinions on learning web3

These are opinions from our own builds, labeled as such. Take the ones that fit how you work.

  1. (Opinion.) Build small things all the way through. Ten finished weekend scripts teach more than one abandoned dashboard, because finishing is its own skill and the small ones all get to the deploy step.
  2. (Opinion.) Put something on a testnet every week. Weekly deploys in tiny sizes beat monthly marathons; the cadence keeps tooling friction from rebuilding itself between sessions.
  3. (Opinion.) Enter hackathons for the reps, not the prizes. Prize pools attract teams who already ship fast. Your first three hackathons are practice loops, and judging your learning by them makes the practice worse.
  4. (Opinion.) Read contracts before writing them. An hour in a verified contract on your target chain shows you the patterns and the failure modes faster than another tutorial chapter.
